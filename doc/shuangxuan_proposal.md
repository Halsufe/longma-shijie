# 学术导师双选功能需求文档

> 文档版本：v0.1  
> 编写日期：2026-08-17  
> 适用模块：学术导师双选  
> 关联现状：`backend/app/api/routes/teachers.py`、`backend/app/api/routes/applications.py`、`backend/app/models/teacher.py`、`backend/app/models/user.py`、`backend/app/models/achievement.py`、`frontend/js/views/mentorship.js`

## 1. 文档目的与范围

本文档定义英才班学生学术导师双选的业务规则、页面行为、数据结构、接口边界、权限、通知、审计和验收标准。该功能建立在现有教师资源库、学生成长档案和导师匹配能力之上，采用管理员维护批次名单、学生填报志愿、导师选择学生、系统按学生志愿顺序汇总、管理员发布结果的流程。

### 1.1 本期范围

1. 管理员创建双选批次，配置各阶段时间，导入学生名单并指定参与导师。
2. 仅支持英才班大一升大二在读学生参加；校友不能参加。
3. 学生主选阶段填写 3 至 4 个不同导师志愿，填写统一个人陈述和每位导师的申请理由。
4. 学生可在申请截止前保存、撤回和重新提交；截止后自动锁定。
5. 导师查看选择自己的学生成长档案，逐人接收/拒绝并提交拟接收名单，每位导师最多 4 人。
6. 系统按学生志愿顺序确定唯一导师，主选结果自动发布；主选未匹配学生进入固定一轮补录。
7. 补录时学生至少选择 1 位导师，不设最多志愿数；导师再次选择，名额为主选后剩余名额。
8. 补录结果必须全部匹配后才可发布和结束；未全部匹配时系统禁止结束，管理员延长补录流程。
9. 支持站内通知、CSV/Excel 名单导入、CSV/Excel 结果导出和全流程审计。
10. 双选流程替代原“交流申请”流程；原交流申请入口、接口和历史数据均按迁移方案删除。

### 1.2 本期不实现

- 不实现基于学生画像或推荐算法的志愿推荐；后续可在双选入口增加辅助建议。
- 不实现平台内预约、面试、沟通记录和评价；导师与学生自行线下沟通或面试。
- 不允许管理员直接把学生指派给导师，不提供超出导师名额的特批。

## 2. 现状与改造思路

### 2.1 现有能力

| 领域 | 现有能力 | 双选复用方式 |
| --- | --- | --- |
| 教师资源 | 教师资料、研究方向、标签、教师搜索和匹配 | 作为批次导师候选；教师自行维护职称、院系、简介、研究方向和标签 |
| 学生档案 | 用户资料、成果档案、成果审核和证明附件 | 选择阶段向对应导师展示个人简介、个人陈述、课程成绩、已审核成果及证明附件 |
| 教师系统 | `mentorship.js`、教师方向、交流申请、学习计划 | 双选入口替代交流申请入口；学习计划保留 |
| 管理端 | 用户导入预检、CSV 导出、教师和成果管理 | 扩展双选批次、名单导入、汇总和导出 |
| 通知与审计 | 站内通知、`audit_logs` | 复用通知中心和审计日志，不新增短信/邮件通道 |

### 2.2 改造原则

1. 双选数据按批次隔离，历史批次永久保留；同一时间只允许一个进行中的批次。
2. 学生志愿顺序对导师不可见，导师只能看到选择自己的学生及该学生给自己的理由。
3. 所有截止时间和权限判断以后端服务器时间为准，时区使用 `Asia/Shanghai`。
4. 名额在数据库事务中校验，任何接口都不能绕过每位导师最多 4 人的限制。
5. 主选不做自动递补；学生从多个导师拟接收名单中按最高志愿匹配后，其他释放名额留给补录。
6. 结果发布由系统按批次配置的发布时间自动执行；管理员可在汇总页查看，但不能修改匹配结果。

## 3. 角色与权限

| 角色 | 批次 | 学生名单 | 导师名单 | 学生填报 | 导师选择 | 结果 | 档案 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| admin | 创建、配置、延长、重新开放、撤回、发布和结束 | CSV/Excel 导入、预检、确认、移除未开始批次名单 | 从教师库勾选 | 查看全部 | 查看全部选择数据；不能代替导师选择 | 查看汇总、导出；不能人工改配 | 查看全部，并可导出 |
| student | 查看参与批次 | 仅查看自己的资格 | 不适用 | 主选填 3-4 个；补录至少 1 个；按阶段保存/撤回/提交 | 不适用 | 仅查看本人最终导师或未匹配状态 | 维护本人资料，查看本人档案 |
| teacher | 查看参与批次和阶段 | 不适用 | 管理员指定后参加 | 不适用 | 仅查看选择自己的学生；接收/拒绝；保存并提交最多 4 人名单 | 查看自己最终接收学生 | 选择阶段查看候选档案；发布后仅保留最终匹配学生 |

### 3.1 数据可见性

导师在选择阶段可查看候选学生的：姓名、学号、班级、专业、联系方式（手机号、邮箱）、个人简介、统一个人陈述、针对该导师的申请理由、学生自主填写的课程成绩（至少 3 门）和已审核通过的成果及证明附件。导师不能查看该学生的其他导师志愿、志愿顺序或给其他导师填写的理由。

主选结果发布后，导师只能继续查看最终匹配自己的学生；未匹配学生及被其他导师录取的学生档案不再对该导师可见。管理员查看全部数据。学生仅查看本人数据和最终结果。

## 4. 批次与状态流转

### 4.1 批次配置

管理员创建批次时填写：

| 配置项 | 规则 |
| --- | --- |
| 批次名称 | 必填，同一进行中批次内唯一 |
| 学年/学期 | 用于批次识别和历史查询 |
| 学生填报开始/截止时间 | 主选必填；截止后学生不可修改 |
| 主选导师选择开始/截止时间 | 主选必填；截止后使用导师最后保存的名单 |
| 主选结果发布时间 | 系统自动发布，发布时间不得早于导师选择截止时间 |
| 补录学生填报开始/截止时间 | 主选结果发布后启用 |
| 补录导师选择开始/截止时间 | 补录必填；截止后使用导师最后保存的名单 |
| 补录结果发布时间 | 只有全部学生匹配时才自动发布 |
| 参与学生名单 | 管理员导入后可查看、移除未开始批次的名单 |
| 参与导师名单 | 管理员从教师资源库勾选 |

一个批次只能有一组主选和一轮补录。批次创建后可在正式开始前编辑配置；阶段开始后，管理员可按规则延长或重新开放阶段。

### 4.2 状态

| 状态 | 进入条件 | 主要行为 |
| --- | --- | --- |
| `draft` 草稿 | 管理员创建批次 | 配置时间、导入学生、选择导师；不对学生/导师开放 |
| `student_apply` 学生填报 | 到达学生填报开始时间 | 学生可保存草稿、提交、撤回和重新提交 |
| `mentor_select` 导师选择 | 学生截止时间到达 | 学生只读；导师可接收/拒绝、保存和提交拟接收名单 |
| `main_published` 主选结果已发布 | 导师截止时间到达并自动计算 | 主选结果自动发布；已匹配学生锁定，未匹配学生进入补录 |
| `supplement_student_apply` 补录填报 | 主选结果发布且配置补录时间 | 仅未匹配学生重新选择，至少 1 个志愿 |
| `supplement_mentor_select` 补录导师选择 | 补录学生截止时间到达 | 仅有剩余名额的导师参与选择 |
| `supplement_published` 补录结果已发布 | 补录截止时全部学生均匹配 | 自动发布最终结果 |
| `completed` 已结束 | 补录结果发布后 | 结果只读，批次进入历史 |
| `reopened` 重新开放 | 管理员撤回结果并重新开放 | 原结果作废；重新配置阶段和时间后再计算 |

主选阶段允许存在未匹配学生，因此主选可正常发布并进入补录。补录截止时如仍有未匹配学生，系统取消自动发布、阻止批次结束并通知管理员；管理员必须延长补录阶段，直到全部学生匹配。

### 4.3 开放前校验

1. 学生名单至少包含 1 名有效学生，导师名单至少包含 3 名有效教师，否则不能开启主选学生填报。
2. 补录开放前，系统校验剩余导师总名额不少于未匹配学生人数；不足时禁止开启补录并提示管理员扩充可参与导师或处理名单。
3. 补录期间即使总名额足够，因导师拒绝仍出现未匹配时，也不得由管理员直接指派，必须延长补录阶段重新选择。

## 5. 学生端需求

### 5.1 资格与档案准备

参与资格完全以管理员导入的名单为准。系统同时要求学号关联现有、正常启用、角色为 `student` 的账号；不存在、重复或状态不合规的记录不能确认导入。

学生在提交正式志愿前应完善以下档案：

| 字段 | 规则 |
| --- | --- |
| 手机号 | 可选格式校验 |
| 邮箱 | 可选格式校验 |
| 专业 | 沿用现有资料字段 |
| 个人简介 | 必填，无字数限制 |
| 课程成绩 | 自主填写想展示的科目，至少 3 门；不限制科目名称；不填写 GPA |

课程成绩建议存储为可扩展列表 `{course_name, score, remark?}`。系统不规定课程名称、分制或统一评分范围，但每条记录须有课程名称和成绩文本。

### 5.2 主选填报

1. 学生查看当前批次可参与导师列表，列表展示姓名、职称、院系、个人简介、研究方向、方向标签、当前申请人数和剩余可接收名额。
2. 学生选择 3 至 4 位不同导师并排序，不能重复选择同一导师。
3. 学生填写一份统一个人陈述，并针对每位选择的导师填写申请理由。
4. “保存草稿”不要求满足正式提交条件；“正式提交”必须满足 3-4 个志愿、统一个人陈述、每位导师理由和课程成绩至少 3 门。
5. 正式提交后，申请截止前仍可撤回并重新编辑、重新提交；系统保留最新版本并记录每次操作审计。
6. 截止时间到达后，学生端自动关闭新增、编辑、撤回和重新提交，仅可查看最终提交内容。
7. 学生不能查看任何导师已选择的学生、导师对其他学生的判断、其他学生的志愿或自己的匹配计算过程。

### 5.3 补录填报

1. 主选结果发布后，仅未匹配学生进入补录。
2. 补录学生只能从有剩余名额的导师中选择，至少选择 1 位；不设最多志愿数量。
3. 补录重新填写志愿顺序、统一个人陈述和每位导师的申请理由；主选内容可复制后编辑。
4. 补录截止前可以保存、撤回和重新提交；截止后自动锁定。
5. 已在主选匹配的学生不能参加补录。

## 6. 导师端需求

### 6.1 候选学生

导师仅能查看选择自己的学生，列表展示学生姓名、学号、班级、联系方式、个人简介、统一个人陈述、针对本导师的申请理由、课程成绩、已审核成果和证明附件。系统不得返回该学生的其他志愿及排序。

列表同时展示：当前选择自己的正式提交人数、导师剩余名额、已接收人数、待处理人数。申请人数只统计正式提交记录，不统计草稿。

### 6.2 选择与提交

1. 导师可对每位候选学生标记“接收”或“拒绝”，并在导师选择截止前反复修改。
2. 导师拟接收名单最多 4 人，可以少于 4 人或为空。
3. 导师点击“最终提交”后锁定名单；未点击最终提交的，截止时间到达时使用最后一次保存的名单。
4. 截止后导师不能再修改。系统将名单快照写入批次汇总，并记录名单版本、操作人和时间。
5. 主选阶段导师不能看到最终匹配结果，直至系统按发布时间发布；补录同理。
6. 补录导师只处理仍有名额的导师，补录名额为该导师主选实际匹配人数与 4 的差值。

## 7. 匹配与结果管理

### 7.1 主选匹配

导师选择截止后系统自动计算：

1. 读取每位导师最后保存或最终提交的拟接收名单；每位导师名单最多 4 人。
2. 对每名学生，收集其出现在多个导师拟接收名单中的导师集合。
3. 按该学生志愿顺序选择排名最高的导师，形成唯一匹配。
4. 学生未进入任何导师名单时标记为“未匹配”。
5. 因学生优先志愿匹配到其他导师而释放的导师名额不在主选阶段自动递补，留给补录。
6. 系统生成主选汇总供管理员查看，并在配置的主选结果发布时间自动发布。

### 7.2 补录匹配

补录采用与主选相同的“导师拟接收 + 学生志愿顺序”规则：

1. 仅处理主选未匹配学生和有剩余名额的导师。
2. 学生被多个导师接收时，按补录志愿顺序确定一个导师。
3. 导师名额按整个批次累计，主选已接收人数加补录接收人数不得超过 4。
4. 计算后必须全部学生匹配；若不满足，系统不发布结果、不结束批次，管理员延长补录阶段后重新填报和选择。
5. 补录完成后系统自动发布最终结果并将批次置为 `completed`。

### 7.3 撤回与重新开放

管理员可以撤回已发布结果并重新开放流程。原结果立即作废，不再作为有效结果展示，但保留结果快照摘要和审计记录。管理员选择重新开放的阶段（学生填报或导师选择），重新配置后续时间；重新计算后产生新的结果版本。

## 8. 管理端需求

### 8.1 批次管理

- 创建、编辑、查看、启动、延长、重新开放、撤回和结束批次。
- 展示批次状态、阶段倒计时、学生提交率、导师提交率、候选总数、已匹配数、未匹配数和名额使用情况。
- 同一时间禁止创建第二个进行中的批次。
- 管理员不能在汇总页面手动修改学生导师归属，不能突破导师 4 人上限。

### 8.2 学生名单导入

支持 CSV 和 Excel。文件至少包含：学号、姓名、班级。导入以文件为资格来源，班级字段随批次保存；系统不额外推断英才班或年级。

导入必须经过“预检 -> 确认”两阶段：

| 校验 | 处理 |
| --- | --- |
| 学号不存在 | 错误，禁止确认 |
| 学号重复 | 错误，禁止确认 |
| 姓名与现有用户不一致 | 错误，禁止确认 |
| 账号非 `student`、非 `active` 或已删除 | 错误，禁止确认 |
| 同一批次重复导入 | 提示重复，禁止产生重复参与记录 |

预检结果展示新增、重复、错误行和错误原因；存在错误时不能确认导入。导入、确认、移除名单均记录审计。

### 8.3 导师名单

管理员从教师资源库勾选参与导师，展示姓名、职称、院系、研究方向和当前状态。只能选择有效教师账号；不支持批量文件导入导师名单。

### 8.4 汇总与发布

管理员可查看但不能改写：

- 学生最终志愿（含每位导师理由）。
- 导师最后保存/最终提交的接收和拒绝名单。
- 主选和补录匹配结果、导师名额使用、未匹配列表。
- 各阶段提交率和时间。

结果发布由系统自动执行。管理员可配置或延长时间，不能绕过补录全部匹配条件直接发布。

### 8.5 导出

支持 CSV 和 Excel，管理员可按批次导出：

1. 参与学生名单。
2. 参与导师名单和名额使用。
3. 学生完整志愿及逐导师理由。
4. 导师拟接收/拒绝名单。
5. 主选结果、补录结果和最终结果。
6. 未匹配列表及补录状态。

导出文件按照管理员权限生成，写入导出审计；文件不得对学生或导师开放批量下载。

## 9. 数据模型

以下模型为建议实现，沿用项目 SQLAlchemy + Alembic 方式。

### 9.1 `mentor_selection_batches`

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | int PK | 批次 ID |
| `name` | varchar(200) | 批次名称 |
| `academic_year` | varchar(20) | 学年 |
| `term` | varchar(20) | 学期 |
| `status` | varchar(40) | 批次状态 |
| `student_apply_start/end` | datetime | 主选学生填报时间 |
| `mentor_select_start/end` | datetime | 主选导师选择时间 |
| `main_publish_at` | datetime | 主选自动发布时间 |
| `supplement_student_start/end` | datetime | 补录学生填报时间 |
| `supplement_mentor_start/end` | datetime | 补录导师选择时间 |
| `supplement_publish_at` | datetime | 补录自动发布时间 |
| `created_by` | int FK users.id | 创建管理员 |
| `created_at/updated_at` | datetime | 时间戳 |
| `deleted_at` | datetime nullable | 软删除 |

### 9.2 `mentor_selection_students`

批次学生关系表：`batch_id`、`student_id`、`student_no_snapshot`、`name_snapshot`、`class_name`、`status`（eligible/submitted/matched/unmatched）、`created_at`、`updated_at`。同一批次同一学生唯一。

### 9.3 `mentor_selection_mentors`

批次导师关系表：`batch_id`、`teacher_id`、`quota`（固定 4）、`main_matched_count`、`supplement_matched_count`、`status`、时间戳。`(batch_id, teacher_id)` 唯一。

### 9.4 `mentor_preferences`

学生志愿版本表：

| 字段 | 说明 |
| --- | --- |
| `id` | 主键 |
| `batch_id/student_id` | 所属批次和学生 |
| `round` | `main` / `supplement` |
| `version` | 学生每次提交递增版本 |
| `personal_statement` | 统一个人陈述 |
| `status` | draft/submitted/withdrawn/locked |
| `submitted_at` | 正式提交时间 |
| `created_at/updated_at` | 时间戳 |

志愿明细表 `mentor_preference_items` 保存 `preference_id`、`teacher_id`、`rank`、`reason`。同一版本内导师不能重复，`rank` 从 1 开始连续。

### 9.5 `mentor_selection_decisions`

导师选择快照表：`batch_id`、`teacher_id`、`student_id`、`round`、`decision`（accepted/rejected）、`is_final_submitted`、`saved_at`、`submitted_at`、`version`。截止时使用每位导师最后保存的有效版本；最终提交后版本锁定。

### 9.6 `mentor_match_results`

结果版本表：`batch_id`、`round`、`version`、`student_id`、`teacher_id` nullable、`matched_rank` nullable、`status`（matched/unmatched/void）、`published_at`、`voided_at`。重新开放时原结果标记 `void`，不得继续作为有效结果展示。

### 9.7 用户资料扩展

在 `users.profile_json` 白名单中新增：

- `phone`：手机号。
- `email`：邮箱。
- `bio`：个人简介（沿用或扩展现有字段）。
- `course_grades`：课程成绩列表，至少 3 条，每条包含 `course_name` 和 `score`，不限制科目名称，不新增 GPA 字段。

教师职称、院系、个人简介、研究方向和标签沿用教师资料库字段；教师通过现有个人资料/方向入口维护。

## 13. 校验、安全与审计

### 13.1 业务校验

1. 主选志愿数量为 3-4，补录为 1 个及以上；所有志愿导师必须属于当前批次且不可重复。
2. 主选正式提交必须有统一个人陈述、每位导师理由和至少 3 门课程成绩；草稿不受正式提交校验限制。
3. 学生截止后所有写接口返回“申请阶段已结束”。
4. 导师拟接收名单不得超过 4 人；补录不得超过剩余名额。
5. 主选/补录结果均保证一名学生最多一个导师；一名导师累计最多 4 名学生。
6. 导师选择截止时采用最后保存名单，不因未点击最终提交而丢失数据。
7. 补录全部匹配前不得发布、结束或进入历史完成状态。
8. 撤回或重新开放后，原结果全部作废；任何旧版本不能重新作为有效结果展示。

### 13.2 访问与文件安全

- 成长档案查询复用现有成果权限，仅向当前批次授权导师返回已审核通过成果。
- 证明附件必须经过同一对象权限校验后才能预览或下载，不能通过文件 URL 越权访问。
- 学号、联系方式、成绩和成果均属于个人信息；列表最小化展示，批量导出仅管理员可用。
- 所有导入、查看档案、查看证明附件、导出、提交、发布、撤回和延长操作写入审计日志。

### 13.3 审计事件

建议动作包括：`batch.create/update/start/extend/reopen`、`roster.import_preview/import_confirm/remove`、`preference.save/submit/withdraw`、`decision.save/submit`、`match.calculate/publish/void`、`profile.view/proof.view/export`。审计记录操作者、批次、轮次、对象、时间、结果、IP/会话标识和数据版本摘要。

## 14. 旧交流申请迁移

双选功能上线后，原“交流申请”不再提供新增、接受、拒绝、取消和前端入口。现有交流申请数据按确认结论直接删除，`communication_applications` 相关路由、页面和菜单移除，不迁移为双选结果。上线前应完成一次数据库备份；删除动作和迁移版本写入部署记录。

## 15. 非功能要求

1. 所有阶段切换和自动发布任务可重复执行而不产生重复通知、重复结果或重复名额占用。
2. 截止瞬间以服务端 `Asia/Shanghai` 时间和数据库事务为准；并发保存、提交和发布必须保证最后有效版本唯一。
3. 自动计算失败时批次不得静默发布，应记录错误并通知管理员重试；重试必须幂等。
4. 历史批次、志愿版本、导师选择版本、结果作废版本和审计记录长期保留，查询接口分页返回。
5. 导入、导出和附件查看均应有错误提示，不返回内部堆栈或存储路径。

## 17. 验收标准

### 17.1 批次与权限

- [ ] 管理员可创建一个批次，导入 CSV/Excel 学生名单并预检错误。
- [ ] 管理员可从教师库指定导师；第二个批次不能在前一个批次完成前启动。
- [ ] 非名单学生、校友、非正常学生账号不能进入双选。
- [ ] 学生、导师、管理员看到的数据符合权限矩阵。

### 17.2 学生填报

- [ ] 主选正式提交必须为 3-4 个不同志愿，并有统一陈述、逐导师理由和至少 3 门课程成绩。
- [ ] 学生可在截止前保存、提交、撤回和重新提交；截止后所有写操作被拒绝。
- [ ] 补录仅向未匹配学生开放，至少 1 个志愿，不设最多志愿数。

### 17.3 导师选择与匹配

- [ ] 导师只能查看选择自己的学生，看不到其他志愿和顺序。
- [ ] 导师可反复保存接收/拒绝；最终名单不超过 4 人；未最终提交时使用最后保存名单。
- [ ] 系统按学生志愿顺序为每名学生确定一个导师，主选不自动递补。
- [ ] 主选结果按配置时间自动发布，未匹配学生进入补录。
- [ ] 补录结果未全部匹配时禁止发布和结束，并通知管理员延长流程。
- [ ] 补录全部匹配后自动发布最终结果并结束批次。

### 17.4 管理、隐私与迁移

- [ ] 管理员只能查看汇总，不能人工改配或超额分配。
- [ ] 结果撤回后原结果作废并保留审计记录；重新开放可重新计算。
- [ ] 所有名单、志愿、决策、档案查看、附件查看、导出和结果操作均有审计日志。
- [ ] 旧交流申请入口和接口移除，历史数据按迁移方案删除；双选流程成为唯一导师选择流程。
- [ ] CSV/Excel 导出包含参与名单、志愿、导师选择、结果和未匹配数据，并仅管理员可用。
