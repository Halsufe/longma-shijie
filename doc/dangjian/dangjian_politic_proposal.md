## 1. 文档目的与范围

本文档是独立的扩展需求文档，只描述新增部分：平台服务对象由“党员”扩展为“党员、团员、群众”全覆盖，每位同学可在平台设置/查看自己的政治面貌，参加团学活动/党员活动，查看政治学习资料等。

本期覆盖：

1. 政治面貌：面向全体学生的通用政治面貌字段，学生自助提交、管理员审核、审计留痕。
2. 团学活动：复用现有活动模型，扩展活动类别与参加对象，团员、群众可参与。
3. 政治学习资料：活动学习材料复用现有机制，另新增按政治面貌分发的公共学习资料库。
4. 统计扩展：党员/团员/群众人数、班级分布、团学活动参与率、资料量统计。
5. 成长档案联动扩展：团学活动经历可写入成长档案。
6. AI/Workflow 依赖边界扩展：党建查询 Skill 与 Workflow 事件覆盖政治面貌与团学活动。

本期不覆盖：

- 既有党建模块的内部重构；`party_json`、`party_*` 表、既有接口保持兼容。
- 创新项目空间、竞赛推荐/导师匹配 Skill 等其他模块。
- 党建查询 Skill 与 Workflow 调度器的内部实现（只定义依赖边界）。

本期落地方式（已确认）：

- 新增通用政治面貌字段，`party_json` 继续保存党员细分档案。
- 学生可提交政治面貌设置/修改，管理员审核后生效，历史变更保留审计。
- 复用 `party_activities`，扩展活动类别与参加对象。
- 学习资料包含活动资料与政治学习资料公共库。
- 团学活动可联动成长档案；群众可参加公开团学活动；统计覆盖全部政治面貌。

## 2. 现状与改造思路

### 2.1 现状

| 现有能力 | 现状 | 扩展方式 |
| --- | --- | --- |
| `users.party_json` | 仅存党员身份（党员类型、申请状态、发展阶段时间轴） | 保留不动，新增通用政治面貌字段 |
| `party_activities` | 活动类别：组织生活会/主题党日/理论学习/志愿公益/发展工作/民主评议/专题教育/其他 | 扩展“团学活动”类别 |
| 参加对象 | 全体党员/党员与积极分子/预备党员与积极分子/全体学生/指定人员 | 扩展“全体团员”“群众” |
| `party_activity_participants` | 报名/取消/签到/考勤 | 复用，报名校验增加政治面貌判定 |
| `party_materials` | 党员发展材料（涉敏，不进知识库） | 保留不动 |
| 班级知识库 | 活动学习材料进入 `class` 知识库 | 复用；新增政治学习资料公共库 |
| 党建查询 Skill / Workflow | 只读查询工具与 5 个事件边界 | 扩展政治面貌与团学活动相关能力 |

当前非党员学生没有政治面貌字段，无法进入党团功能；团学活动也没有独立入口和统计。

### 2.2 改造思路

- `users` 新增 `political_status`（默认“群众”）与 `political_status_updated_at`；新增 `political_status_reviews` 审核表。
- 学生自助提交，管理员审核生效；同状态重复提交拒绝；审核只允许一次；变更写审计。
- `party_activities.category` 增加“团学活动”；`target_roles` 增加“全体团员”“群众”。
- 新增政治学习资料公共库，管理员发布并指定适用对象，学生按政治面貌可见（推荐 `political_materials` 表，见待确认事项）。
- 统计接口扩展政治面貌维度，管理端可看党员/团员/群众分布。
- 成长档案联动支持团学活动经历。
- Skill 与 Workflow 扩展边界，不改既有事件与工具兼容性。

## 3. 角色与权限

| 角色 | 政治面貌与党团权限 |
| --- | --- |
| 学生（含群众） | 查看本人政治面貌；提交设置/修改（待审核）；查看并报名符合参加对象的党团活动；查看适用范围内的政治学习资料；查看本人参与记录 |
| 学生党员/团员 | 在通用学生权限之上，可查看并报名面向党员/团员的专属活动，查看党员/团员专属学习资料 |
| 管理员（admin） | 审核政治面貌变更；维护政治学习资料；管理团学活动（复用现有活动管理）；查看全员政治面貌与党团统计 |
| 教师（teacher） | 默认不参与党团管理，不可查看党员名册与政治面貌明细；是否可查看公开活动/公开资料见待确认事项 |
| 校友（alumni） | 不开放党团功能，沿用现有决策 |

权限隔离原则：

- 政治面貌明细与统计仅本人和 `admin` 可见。
- 党员名册、党员统计、党员发展材料继续仅 `admin` 可见，群众/团员不可越权。
- 党团活动与学习资料按 `target_roles`/适用对象做可见性与报名校验。

## 5. 政治面貌字段定义

### 5.1 users 表扩展

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `political_status` | String(30)，默认“群众” | 枚举：中共党员/预备党员/入党积极分子/共青团员/群众（是否包含民主党派/无党派人士见待确认事项） |
| `political_status_updated_at` | DateTime | 政治面貌最近生效时间 |

> `party_json` 保持不变，继续保存党员细分档案（党员类型、申请状态、阶段时间轴）。

### 5.2 政治面貌审核表 political_status_reviews

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | int | 主键 |
| `user_id` | int | 申请学生（FK users.id） |
| `from_status` | str | 原政治面貌 |
| `to_status` | str | 申请的政治面貌 |
| `status` | str | `pending/approved/rejected` |
| `submitted_by` | int | 提交人（默认本人） |
| `submitted_at` | datetime | 提交时间 |
| `reviewed_by` | int | 审核管理员（可空） |
| `reviewed_at` | datetime | 审核时间（可空） |
| `remark` | text | 申请说明/审核意见 |

交互需求：

1. 学生首次设置或修改政治面貌均提交申请，状态 `pending`。
2. 管理员审核通过后，更新 `users.political_status` 与 `political_status_updated_at`，并写审计日志。
3. 审核拒绝时保留原政治面貌，可在申请说明中填写拒绝原因。
4. 同状态重复提交拒绝；一条申请只能审核一次。
5. 学生个人中心展示政治面貌、生效时间与最近一次申请状态。

## 6. 党建活动扩展为党团活动

### 6.1 活动类别扩展

`party_activities.category` 增加“团学活动”。

- 前端展示名统一调整为“党团活动”或“党建活动/团学活动”两类入口。
- 内部表名、路由前缀 `party_*` 保持不变，避免破坏既有实现。
- 是否细分“主题团日/团学实践”等子类见待确认事项。

### 6.2 参加对象扩展

| `target_roles` 值 | 含义 |
| --- | --- |
| 全体党员 | 正式党员、预备党员 |
| 党员与积极分子 | 正式党员、预备党员、入党积极分子 |
| 预备党员与积极分子 | 预备党员、入党积极分子 |
| 全体团员 | 政治面貌为共青团员的学生 |
| 党员与团员 | 党员（含预备/积极分子）+ 共青团员 |
| 全体学生 | 所有在校学生（含党员、团员、群众） |
| 群众 | 仅政治面貌为群众的学生（不含党员、团员） |
| 指定人员 | `target_member_ids` 指定用户 |

### 6.3 活动管理

1. 管理员创建团学活动时选择类别“团学活动”并设置参加对象。
2. 报名/签到/取消/考勤复用现有 `party_activity_participants` 流程。
3. 活动可见性：面向“全体学生”的活动所有在校学生可见；党员/团员专属活动仅符合对象可见。
4. 活动状态流转与归档沿用现有机制。

## 7. 报名与签到扩展

1. 报名校验增加政治面貌判定：学生的 `political_status` 必须满足活动的 `target_roles`。
2. 群众可报名“全体学生”“群众”活动；团员可报名“全体团员”“党员与团员”“全体学生”活动。
3. 签到窗口、自助签到、管理员代签/补签/缺席逻辑沿用现有实现。
4. 本人参与记录同时包含党建活动与团学活动。

## 8. 学习资料

### 8.1 活动资料（复用）

团学活动学习材料随活动 `materials_json` 进入班级知识库，沿用现有逻辑；党员发展材料仍不进入知识库。

### 8.2 政治学习资料公共库（新增）

需求：

1. 管理员发布政治学习资料，并指定适用对象（全体党员/全体团员/全体学生/群众/指定人员）。
2. 学生只能查看适用对象包含本人政治面貌的资料。
3. 资料支持标题、说明、附件（PDF/JPG/PNG，单文件不超过 20MB）、发布状态与上下架。
4. 前端新增“政治学习资料”入口（学生党团页与管理端）。

存储建议：

- 推荐新增 `political_materials` 表：`title`、`description`、`applicable_roles_json`、`attachments_json`、`status`、`created_by`、`created_at/updated_at/deleted_at`。
- 备选方案：复用现有知识库或资源社区并增加“适用政治面貌”过滤；最终方案见待确认事项。

## 9. 统计与分析扩展

管理端统计扩展以下维度：

| 统计项 | 口径（推荐） |
| --- | --- |
| 政治面貌分布 | 按 `political_status` 分组：中共党员/预备党员/入党积极分子/共青团员/群众 |
| 班级/年级分布 | 按 `class_name`/`grade` 分组 |
| 团学活动参与率 | 仅统计类别为“团学活动”的活动，分母为应参加名单（`target_roles`/`target_member_ids` 展开） |
| 资料统计 | 活动学习材料 + 政治学习资料数量，按年月/类别统计 |
| 发展情况 | 保持现有 `apply_status` 统计 |

筛选参数：班级、年级、年份、活动类别、政治面貌。

> 统计口径以 `political_status` 为准；`party_json` 作为党建管理档案（口径冲突处理见待确认事项）。

## 10. 与成长档案联动扩展

1. 团学活动完成签到后，可一键写入成长档案，按活动性质选择“组织管理（organization）”或“社会实践（social）”，状态 `pending`。
2. 复用现有 `source_type="party"`、`source_id` 防重机制；活动性质由管理员在发布/联动时指定（见待确认事项）。
3. 团员身份不写入成长档案（推荐，见待确认事项）。
4. 党员身份联动保持现状。

## 11. AI 对接与依赖关系

本章只定义依赖边界，具体设计后续单独细化。

### 11.1 党建查询 Skill 扩展

- 新增只读能力：本人政治面貌查询、团学活动查询、政治学习资料查询。
- 权限：本人可查询自己的政治面貌与参与记录；管理员可查询政治面貌统计；活动与资料按可见性过滤。
- 写操作不开放；触发词、提示词、返回格式由后续文档细化。

### 11.2 Workflow 事件边界扩展

- 新增 `political_status_change_approved` 事件：政治面貌审核通过后通知本人。
- 既有 `party.activity_published`、`party.registration_deadline_approaching`、`party.activity_starting`、`party.activity_finished` 事件自动覆盖团学活动（同一张活动表）。
- 只定义事件名与载荷；调度、幂等任务记录、失败重试由 Workflow 文档细化。

## 12. 数据模型与接口落地说明

### 12.1 数据模型

- `users` 新增 `political_status`、`political_status_updated_at`。
- 新增 `political_status_reviews` 表。
- `party_activities` 枚举扩展（`category`、`target_roles`），无表结构变更。
- 新增 `political_materials` 表（推荐，见待确认事项）。

### 12.2 接口清单（概要）

| 方法 | 路径 | 权限 | 说明 |
| --- | --- | --- | --- |
| GET | `/api/v1/party/political-status/mine` | 本人 | 本人政治面貌与申请状态 |
| POST | `/api/v1/party/political-status/mine` | 本人 | 提交政治面貌设置/修改 |
| GET | `/api/v1/party/political-status/reviews` | admin | 政治面貌审核列表（含筛选/分页） |
| PUT | `/api/v1/party/political-status/reviews/{id}/approve` | admin | 审核通过并生效 |
| PUT | `/api/v1/party/political-status/reviews/{id}/reject` | admin | 审核拒绝 |
| GET | `/api/v1/party/learning-materials` | 登录用户（按适用对象） | 政治学习资料列表 |
| POST | `/api/v1/party/learning-materials` | admin | 发布政治学习资料 |
| PUT | `/api/v1/party/learning-materials/{id}` | admin | 编辑/上下架 |
| DELETE | `/api/v1/party/learning-materials/{id}` | admin | 软删除 |
| GET | `/api/v1/party/stats` | admin | 扩展 `political_counts` 等统计类型 |

### 12.3 前端

- 学生个人中心：政治面貌展示与修改提交入口。
- 学生党团页：活动列表增加“团学活动”类别筛选；新增“政治学习资料”区块。
- 管理端：新增“政治面貌审核”区块；学习资料管理；统计扩展。

## 13. 校验规则汇总

| 规则 | 约束 |
| --- | --- |
| 政治面貌 | 仅允许 中共党员/预备党员/入党积极分子/共青团员/群众（可扩展） |
| 修改提交 | 同状态重复提交拒绝；提交后状态为 `pending` |

| 资料可见性 | 仅展示适用对象包含本人政治面貌的资料 |
| 附件 | 沿用 PDF/JPG/PNG，单文件不超过 20MB（可配置） |
| 成长档案联动 | 团学活动完成签到后才可写入，状态 `pending`，`source` 标记防重 |

## 14. 待确认事项

以下事项用户未明确，本文档给出推荐默认值，评审时确认：

1. 政治面貌枚举：推荐暂为 中共党员/预备党员/入党积极分子/共青团员/群众；是否包含“民主党派/无党派人士”待确认。
2. 初始设置审核：推荐首次设置与修改一样需要管理员审核。
3. “群众”参加对象语义：推荐仅非党员、非团员学生；公开活动统一用“全体学生”。
4. 团学活动类别：推荐先只增加“团学活动”，是否细分“主题团日/团学实践”等子类待确认。
5. 政治学习资料存储：推荐新增 `political_materials` 表；备选复用知识库/资源社区。
6. 团学活动联动分类：推荐管理员在发布/联动时指定“组织管理/社会实践”。
7. 团员身份是否写入成长档案：推荐不写入，仅活动经历联动。
8. 教师/校友可见范围：推荐教师仅可见公开活动与公开资料，校友不开放党团功能。
9. 统计口径：推荐以 `political_status` 为准；与 `party_json` 不一致时按政治面貌统计。
10. 政治面貌审核通过通知：推荐通知本人，是否通知其他角色待确认。

## 15. 验收要点

1. 每位学生可在平台查看并提交政治面貌，管理员审核后生效，审计留痕。
2. 管理员可发布团学活动并设置参加对象（团员/群众/全体学生等），学生按政治面貌报名签到。
3. 群众可参加公开团学活动，不能查看党员名册与党员统计。
4. 政治学习资料按适用对象可见，学生不能越权查看。
5. 管理端统计覆盖党员/团员/群众人数、班级分布、团学活动参与率、资料量。
6. 团学活动完成签到可一键写入成长档案（`pending`）。
7. 既有党建功能不受影响：`party_json`、党员名册、党建活动、Skill、Workflow 事件兼容。
8. AI Skill 支持政治面貌与团学活动只读查询（依赖边界）。
9. 全部接口权限校验生效，越权访问返回 403。
